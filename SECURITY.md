# Security policy

Trailkeep is designed for regulated environments, so we treat security reports as the highest-priority
input the project receives.

## Reporting a vulnerability

Please **do not** open a public issue. Use GitHub's private vulnerability reporting for this repository
(**Security → Report a vulnerability**). Include what you found, how to reproduce it, the version or commit,
and any suggested fix.

What to expect:

| Step | Target |
|---|---|
| Acknowledgement | within 3 business days |
| Triage and severity assessment | within 7 days |
| Fix or mitigation for confirmed issues | within 90 days, sooner for critical issues |
| Public advisory | published with the fix release, with credit to the reporter unless they prefer otherwise |

We request CVE identifiers through GitHub for confirmed vulnerabilities and publish advisories on the
repository's Security tab.

## Scope

In scope: the application code, its container image, its deployment manifests, its build and CI
configuration, and its dependencies as pinned in `pom.xml`.

Out of scope: vulnerabilities that require a compromised identity provider, database administrator or
cluster administrator; findings in third-party services the deployment integrates with (IdP, SMTP relay,
ClamAV) that are not caused by how Trailkeep uses them; and reports generated by running automated scanners
without a demonstrated impact.

## Supported versions

Until 1.0.0 is released, only the `main` branch is supported. After 1.0.0, the latest minor release
receives security fixes.

## Our own controls

Every pull request runs static analysis (CodeQL, Semgrep, SpotBugs/FindSecBugs), secret scanning and
dependency checks; `main` additionally runs SonarCloud, Dependency-Check and container scans; nightly builds
run an authenticated OWASP ZAP scan. A software bill of materials and signed provenance ship with every
release. Details: `IMPLEMENTATION_PLAN.md` Part G and `BUILD_PLAN.md` §9 and §12.
